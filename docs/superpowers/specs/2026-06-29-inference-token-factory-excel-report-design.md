# 推理 Token 工厂 Excel 汇报初版设计

- 日期：2026-06-29
- 版本：v2.0-design
- 范围：`inference-report/` 下推理相关资料、`data/` 与 `outputs/` 下已有性能和上下文分析数据
- 目标产物：多 Sheet Excel 汇报工作簿初版，后续可补充 Word/PPT 正文

## 1. 背景与目标

本报告面向领导汇报，不定位为单项测试报告。开篇先说明工服场景正在形成高 token 消耗、长上下文、高并发的推理压力，需要建设“推理 Token 工厂”，通过推理优化技术提升吞吐、降低显存和算力成本，并形成可复制的资源规划和部署建议。

已有业务背景数据可引用生产上下文分析：最近 90 天约 100.8 万请求、总 token 约 593.6 亿，输入 token 占 98.9%，32K 以上长上下文请求约 62%。这些数据用于说明优化重点应围绕长上下文 prefill、KV Cache、量化和并发吞吐。

## 2. 工作簿总体结构

工作簿采用“领导汇报主线 + 技术专题 + 数据附录”的多 Sheet 结构。前 4 个 Sheet 服务于快速阅读和决策，后续专题 Sheet 承接会议分工和技术证据，最后用数据附录保留可追溯底表。

| Sheet | 名称 | 作用 |
| --- | --- | --- |
| 00 | 目录与版本 | 版本号、目录、负责人、状态说明、数据来源链接 |
| 01 | 背景与目标 | 工服 token 工厂背景、现状数据、优化目标 |
| 02 | 总览结论 | 已验证结论、缺系统数据项、待验证项、本期不重点项 |
| 03 | 技术路线地图 | 各推理优化技术的目标、成熟度、收益预期、资源诉求 |
| 04 | 模型量化 | H200 FP8/BF16 等已有模型量化数据总结和可视化 |
| 05 | KVCache 量化 | fp16/fp8 KV Cache 量化结论、fp4 暂不测试说明、补测计划 |
| 06 | Prefix/KV 命中 | Prefix Cache/KV Cache 命中率结论边界和系统化验证方向 |
| 07 | 投机解码 | 原理、候选 token 数测试方案、待胡正升补充结果 |
| 08 | PD 分离 | Prefill/Decode 分离原理、部署形态、带宽要求、资源申请 |
| 09 | MOE 专家并行 | 当前暂无明确优化结论，本期不作为重点，记录后续关注点 |
| 10 | 连续批处理 | 框架原生支持、无法作为独立开关测试，只说明已具备 |
| 11 | 汇总建议与资源计划 | 研发侧重点、落地优先级、待申请资源、后续里程碑 |
| 12 | 数据附录 | 原始数据汇总、图表底表、字段口径说明 |

## 3. 专题 Sheet 固定模板

每个专题 Sheet 统一使用以下结构，便于横向对比和后续补数据。

| 区块 | 内容要求 |
| --- | --- |
| V2.1 目标 | 说明该技术解决的瓶颈、适用工服场景和预期收益 |
| V2.2 方案 | 写原理、关键参数、部署形态、测试变量和执行方法 |
| V2.3 已有结论/待验证计划 | 有数据则给定量结论；缺数据则标明“有结论但缺系统数据”或“待验证” |
| V2.4 可视化/数据来源 | 放图表、引用的 CSV/XLSX/Word/PPT 资料路径和指标口径 |
| V2.5 建议 | 给出落地优先级、资源诉求、风险和下一步动作 |

状态标签固定为四类：

- 已验证：已有数据可支撑结论，可进入汇总建议。
- 有结论但缺系统数据：可以描述经验结论，但必须标注需补测。
- 待验证：只写原理、方案、资源和指标，不写成确定收益。
- 本期不重点：说明原因和后续关注方向。

## 4. 已有数据与可视化设计

### 4.1 背景数据

使用 `outputs/context_analysis_20260609_034248/` 中的生产上下文分析结果，展示：

- 总请求数、总 token、输入/输出 token 占比。
- 输入 token 区间分布，突出 32K 以上长上下文占比。
- Top 模型请求量和平均 token，用于说明真实业务负载。

建议图表：

- 长上下文请求占比分布条形图。
- 输入/输出 token 占比饼图或堆叠条。
- 模型请求量 Top 5 条形图。

### 4.2 模型量化

使用 `data/H200/32B/1.csv`、`data/H200/32B-FP8/1.csv`、`data/H200/72B/2.csv`、`data/H200/72B-FP8/2.csv` 对比 H200 上 BF16 与 FP8。当前可形成的初步结论：

- 32B/72B 在 H200 上 FP8 相比 BF16，吞吐量整体有明显提升。
- 已抽样计算：72B 在匹配场景下平均吞吐约提升 32%，TPOT 约为 BF16 的 77.5%；32B 平均吞吐约提升 30%，TPOT 约为 BF16 的 77.8%。
- 显存节省约 50% 若来自会议或历史资料，应标注为“历史结论/部署估算”，除非底表中存在显存采集列。

建议图表：

- BF16 vs FP8 吞吐量折线图，横轴为并发数。
- BF16 vs FP8 平均增量时延对比图。
- 关键结论卡：吞吐提升、TPOT 降低、显存节省。

### 4.3 上下文与并发

已有数据中包含不同输入长度、输出长度和并发的测试结果。用于支撑：

- 长上下文场景下 TTFT 增长趋势。
- 并发提升下吞吐与首 token 延迟的权衡。
- 汇报中至少呈现 TPS/Tokens/s、首 token 延迟、平均增量延迟。

建议图表：

- 不同并发下吞吐曲线。
- 不同输入长度下 TTFT 曲线。
- 吞吐量 vs TTFT 双轴图，仅用于展示拐点，不用于过度推断。

## 5. 技术专题内容边界

### 5.1 KVCache 量化

内容包含 KV Cache 从 fp16/bf16 到 fp8 的显存与性能影响，优先写已有 H200 结论。fp4 因 H200 不支持，暂不作为本期测试项。胡正升补充系统测试结果后，回填吞吐、TTFT、TPOT、显存占用和 gpu_cache 利用率阈值影响。

### 5.2 Prefix Cache/KV Cache 命中

当前写法为“有结论但缺系统数据，后续补测”。报告中说明原理：共享系统提示、工具定义和历史上下文可复用 prefix KV，降低重复 prefill 成本。验证方向包括 prefix_ratio、命中率、TTFT 降低比例、缓存占用和不同上下文长度下收益变化。

### 5.3 投机解码

当前主要写原理和测试方案，等待胡正升结果。方案覆盖无投机基线、候选 token 数 1/3/5、不同输入长度和并发，关注 TPOT、吞吐、接受率、单请求延迟和高并发收益衰减。

### 5.4 PD 分离

由孙力光负责方案设计。报告需要明确典型部署：Prefill 节点使用高算力卡如 H200，Decode 节点可使用 H20；典型拓扑可写 4P+2D，也可补充 1P1D、2P1D、1P2D 作为验证梯度。需说明 KV 传输带宽要求、适用场景为大参数和长上下文，并列出当前待申请资源。

监控指标包括 TTFT、TPOT、吞吐、Prefill/Decode GPU 利用率、显存占用、KV 传输延迟和网络带宽。

### 5.5 MOE 专家并行

明确标注“当前无明确优化结论，暂不作为本期重点，后续关注”。只保留基本原理、潜在收益、风险和后续需要结合 MoE 模型及多卡资源验证的方向，避免把未验证内容写成建议落地。

### 5.6 连续批处理

不作为独立测试项。说明 vLLM/SGLang 框架已原生支持连续批处理，通常无法作为“关闭/开启”的独立变量比较。本报告只在能力地图中标注“已具备”，必要时说明相关调度参数会影响吞吐与延迟。

## 6. 输出规则

Excel 初版需要有版本号，建议命名为 `推理token工厂汇报大纲_汇报版_v2.0.xlsx`。后续补充胡正升数据后递增为 v2.1、v2.2。

每个 Sheet 顶部保留：

- 报告版本。
- 更新时间。
- 责任人。
- 当前状态。
- 数据来源。

已有结果必须用图表展示，缺数据部分使用“方案/待验证/资源诉求”表格，不填虚假的数值。所有图表底表集中到 `12_数据附录`，便于追溯和后续更新。

## 7. 角色分工与回填机制

| 角色 | 报告动作 |
| --- | --- |
| 孙力光 | 整合已有推理测试数据、原理、资源评估和自动化脚本；负责报告框架、PD 分离方案、最终汇总 |
| 胡正升 | 补充 KV Cache 量化与投机解码测试方案和分析结论，回填吞吐、延迟、显存、命中率等指标 |

回填规则：

- 若结论状态变化，必须同步更新 `02_总览结论` 和 `03_技术路线地图`。
- 版本号按补充内容递增：结构初版为 v2.0；补齐 KV Cache 量化或投机解码任一项后递增为 v2.1；最终汇总版递增为 v2.2。

## 8. 验收标准

1. Excel 至少包含 13 个 Sheet，且首页有目录和版本号。
2. 报告逻辑符合“背景目标 → 调研技术点 → 已具备项结论 → 未具备项方案 → 汇总建议”。
3. 模型量化、上下文、并发等已有数据有可视化图表。
4. KV Cache 量化、Prefix/KV 命中、投机解码、PD 分离、MOE 专家并行、连续批处理均有明确状态标签。
5. 缺系统数据的部分不能写成已验证收益，必须包含补测计划、指标和资源诉求。
6. 指标至少包含吞吐量 TPS/Tokens/s、首 token 延迟、平均增量延迟；有条件时补充显存、GPU 利用率和缓存命中率。
7. 文件可作为本周初稿交付，后续能在不改结构的情况下回填胡正升的 KV Cache 量化和投机解码结果。
